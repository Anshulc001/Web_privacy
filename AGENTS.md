# AGENTS.md — WebGuard

Read this file first. It is the source of truth for how to work on this project.
`README.md` is for end users, `INSTALL.md` is for installing the extension, and this
file is for whoever (human or AI) changes the code.

## Session protocol (do this every session)

1. **Read this file first**, fully, before touching code. Do not rely on chat history
   or on memory of a previous session.
2. **Read the Current state block below**, then run `npm run agents:check`. If it says
   the block is stale, run `npm run agents:state` (see step 6).
3. **Check what is actually there.** Run `git status`, `git diff`, and read the files
   the request touches. The repository is the truth and this file is the map; when they
   disagree, fix the map.
4. **Recheck the implemented behavior** against the request and against the invariants
   in this file (privacy contract, rule budgets, counting semantics) before planning.
5. **Do the work** in small steps, verifying with the narrowest useful check
   (`node --test tests/<file>.test.mjs`, `node --check <file>`, `npm run build:data`).
6. **Before finishing, update the record.** Add a dated entry under "Recent changes"
   with what changed, what was verified and what is still open. If the version, rules,
   data dates, retention default, permissions or test count changed, run
   `npm run agents:state` and keep the updated block. Then run `npm test`.
7. **Report honestly:** what changed, which checks passed, which could not run.

## What this project is

WebGuard is a Chrome Manifest V3 privacy/security extension. It shows cookies,
permissions, domain registry data, a suspicious-site score, breach matches and
visit/blocked counts for the current site; blocks known ad/tracker hosts; and renders
a full-tab dashboard scoped by a day/week picker.

- Plain ESM JavaScript. No bundler, no framework, no runtime dependencies.
- `manifest.json` at the repository root is the extension. "Load unpacked" points at
  the repo root, never at `dist/`.
- Everything is local. No account, no analytics, no telemetry.

## Project rules (non-negotiable)

1. **No AI attribution in git.** Do not add `Generated with …`, `Co-Authored-By`, or
   any Freebuff/Codebuff line to a commit message or PR. If a commit already has one,
   remove it from history and force-push the cleaned version (only when the user has
   asked for the push).
2. **Local working notes stay out of GitHub.** Scratch notes, test candidate lists and
   investigation logs belong in gitignored files, not in the repository.
3. **Do not claim a browser/UI test you did not run.** State clearly which checks ran
   and which did not.
4. **Small, reversible steps.** Explain what changes and why in simple English before
   or alongside making it. Do not start a risky rewrite without agreeing on the plan.
5. **Preserve existing behavior unless the change is requested.** This codebase encodes
   many deliberate privacy and correctness decisions in comments; read the comment
   before "simplifying" the code.
6. **Do not hand-edit generated data.** `data/ad-tracker-rules.json`,
   `data/ad-tracker-data.json`, `data/cosmetic-rules.json`, `data/cosmetic-generic.css`,
   `data/breach-data.json` and `data/threat-list.json` are build output. Regenerate
   them with the `tools/` script; if the network is unavailable, say so instead of
   faking a rebuild.
7. **Keep the privacy contract.** Never read, store or display cookie values. Store
   hostnames only, never full URLs, query strings or page content. Any new outbound
   network request must be justified, user-visible in the README, and optional where
   possible.

## Architecture and invariants

### Blocking (four layers)

1. **Static ruleset** `data/ad-tracker-rules.json`, referenced by
   `declarative_net_request` in the manifest. Today ~26,000 rules.
2. **Dynamic remote hosts** downloaded as `ad-tracker-data.json` and applied by
   `blocking-manager.mjs`, so the list can update without a new package. 25,000 host
   rules need Chrome 121+ (30,000 safe dynamic rules); `manifest.json` therefore pins
   `minimum_chrome_version: "121"`. Do not lower it without chunking the list.
3. **Allowlist** `allowAllRequests` (priority 10) plus an explicit `allow` rule for
   subresources. Allowlisting covers the exact host and its registrable domain.
4. **Tracking-parameter redirect** (dynamic rule id 950, priority 1) strips
   `utm_*`, `fbclid`, `gclid`, … from top-level and frame navigations. The allowlist
   is excluded from both request and initiator matching.

Rules that matter:

- Chrome guarantees **30,000 static rules**. `build-ad-rules.mjs` publishes at most
  **25,000 host rules** + up to **4,500 path rules** and throws if the total exceeds
  30,000. Never raise these without checking the platform limit.
- Host rules are only emitted from `||host^` / `.host` patterns. Path rules are only
  emitted for `||host/path` patterns, must contain an ad/tracker token, and are
  filtered to stay under budget.
- `@@` exceptions withdraw both the host and the path rule. Do not re-add a withdrawn
  host.
- Loopback (`localhost`, `127.*`, `::1`) is always excluded.
- **A label is not a blocking decision.** `lib/tracker-categories.mjs` decides how a
  *blocked* host is labelled. Its domain lists may only be force-included in the
  blocklist for hosts EasyList itself declares as host-level rules. Inventing a host
  rule for e.g. `facebook.com`, `linkedin.com`, `bing.com` or `disqus.com` would block
  navigating to that site, because these rules include `main_frame`.
- Static rules are installed by Chrome; the downloaded host list is applied as
  **dynamic** rules (ids from 1,000,000). Toggling blocking off must remove/disable
  both, plus the redirect rule.

### Blocked counting

`blocking-counter.mjs` keeps two separate dedupe scopes:

- **Live** (`tabs`, `tabHosts`, in-memory `seenByTab`): the popup and toolbar badge.
  Reset whenever the tab loads a new document.
- **Stored** (`days`, `dayHosts`, `hosts`, `sites[site]`, persisted `seen`): the
  dashboard. One fingerprint per `(site, day, blocked host + pathname)`, so reloading
  a site does not double-count.

Blocked requests are attributed to the page the tab is showing (`tabSites` in the
worker), falling back to `details.initiator` only when the page is unknown. Every
list, chart and total must add up to the displayed number; do not slice rows in the
counter. Writers are serialized through a queue because storage is a read-modify-write.

### Settings and visit records

- Defaults live in `DEFAULT_SETTINGS` (`lib/storage-settings.mjs`):
  retention 168 h, recording on, blocking on, automatic registry lookup on, empty allowlist.
- `autoDomainLookup: false` makes the Domain Info button the only RDAP trigger. The
  lookup itself only ever sends a hostname, never a page URL.
- Retention is whole hours, 24–168. UI shows days, never "168 hours".
- Visit records store hostnames and timestamps only, for the current retention window.
  Incognito tabs are skipped. `historyPaused` stops new records but keeps pruning.
- There is no history browsing UI. The header frame picker (Today / Yesterday / Past
  7 days, default Today) is the only time control: it decides which sites
  `#target-select` offers and which days the KPI totals cover. Sites outside the
  frame disappear from the picker, so the panels cannot show stale scope.

### Cosmetic filtering

`content/cosmetic-filter.js` runs at `document_start` and layers:

1. built-in selectors (`COSMETIC_SELECTORS`),
2. the compiled generic stylesheet (`data/cosmetic-generic.css`),
3. per-host selectors fetched from the worker,
4. a bounded placeholder-label sweep (captions like "Advertisement") that only hides
   a wrapper containing nothing but that caption.

It follows the same switches as blocking: off when WebGuard is off or the site is
allowlisted, including on an already-open page (`storage.onChanged`).

### MV3 worker lifecycle (fragile, read before changing)

- The worker is woken lazily; a worker that starts on a page's first request is too
  late to count it. `content/cosmetic-filter.js` pings at `document_start`,
  `runtime.onStartup` warms settings, and `tabs.onCreated` warms the cache.
- The per-tab count resets on the **main-frame request**, not on commit, so a late
  commit cannot wipe counts that just landed.
- Settings are cached in memory and invalidated by `storage.onChanged`.
- Keep `chrome.*` usage out of `lib/` where possible. `lib/` modules take APIs
  (`storageArea`, `cookiesApi`, `fetchImpl`, `dnr`, `tabs`) as arguments so tests can
  run without Chrome.

### Messaging

Popup and dashboard talk to the worker with `chrome.runtime.sendMessage`. Message
types are guarded in `service-worker.js`; the sender must be this extension and, for
privileged messages, a URL under `chrome.runtime.getURL("")`. When adding a message,
add the handler, the guard, the caller, and a test.

## Data pipeline

| File | Built by | Source |
| --- | --- | --- |
| `data/ad-tracker-rules.json` | `tools/build-ad-rules.mjs` | EasyList + EasyPrivacy |
| `data/ad-tracker-data.json` | same script | same list (hosts + metadata) |
| `data/cosmetic-rules.json`, `data/cosmetic-generic.css` | `tools/build-cosmetic-rules.mjs` | same list |
| `data/breach-data.json` | `tools/build-breach-data.mjs` | Have I Been Pwned |
| `data/threat-list.json` | `tools/build-threat-list.mjs` | Phishing.Database |

Rules for every data file:

- Metadata: `version`, `buildDate` (ISO, not in the future), `checksum`, `source`,
  attribution where required, `stats`.
- `checksum = "sha256:" + sha256(JSON.stringify(canonicalArrayOrObject))`, computed
  with `lib/data-integrity.mjs`. Canonical means sorted/normalized exactly as the
  runtime validator will normalize it.
- Runtime validators (`validateBlockingData`, `validateBreachData`,
  `validateThreatData`) reject bad schema, duplicates, future dates, oversized input
  and checksum mismatches. A rejected download keeps the last good copy.
- `syncFile` in `data-sync.mjs` stores the copy; bundled copies seed first run so the
  extension works offline.
- The daily GitHub Action commits the regenerated files. Data files are minified
  one-line JSON; do not pretty-print them.
- Attribution is required: EasyList (CC BY-SA 3.0 / GPL v3), Phishing.Database (MIT),
  Have I Been Pwned (CC BY 4.0). Keep it in `README.md` and in the metadata.

## Testing

- `npm test` is the real gate. It includes live Chrome tests that load the unpacked
  extension, confirm a tracker really fails with `ERR_BLOCKED_BY_CLIENT`, and drive the
  real popup and dashboard.
- Unit tests build fake `chrome.storage.local`, DNR, cookies and tabs objects. Follow
  that pattern instead of adding a mocking library.
- Chrome's toolbar popup bubble is **not** a Playwright page. The e2e test uses
  `chrome.action.openPopup()` and the CDP `Target.getTargets`/`Target.attachToTarget`
  approach. `context.pages()` will not list it.
- `manifest.test.mjs` pins the approved permission list, content scripts,
  web-accessible resources, CSP, ruleset budget and `minimum_chrome_version`. Update it
  deliberately if a permission actually changes, and update the README permission table
  at the same time.
- `privacy-contract.test.mjs` scans shipped JS for network primitives and hardcoded
  hosts. A new destination fails the test until it is added to
  `lib/privacy-contract.mjs`, which also feeds Dashboard → Settings → Privacy. Add it
  there first, then update the README.
- Browser tests need Playwright's Chromium/Chrome and network access. If they cannot
  run, report that; do not mark them passed.

## Common tasks

**Change what gets blocked**
1. Edit `tools/build-ad-rules.mjs` (selection/patterns/budget).
2. `npm run build:ads`, then check stats: ≤30,000 rules, no duplicate `urlFilter`,
   no loopback, no whole-site domain, all intended tracker hosts present.
3. `npm test` (manifest test validates the ruleset shape).
4. Remember the runtime applies the downloaded `hosts` array as dynamic rules too, so
   the data file and the rules file must describe the same policy.

**Add a UI section**
`dashboard.html` (or `popup.html`) → CSS → `dashboard.js`/`popup.js` → a message type
→ `dashboard-service.mjs` (or `currentSitePrivacy`) → tests. Keep empty, unavailable
and error states distinct; never render "safe".

**Add a data source**
Build script in `tools/` + validator + checksum + `syncFile`/seed wiring +
`describeData` entry + add the file to `update-data.yml` + tests.

**Change settings**
Add to `DEFAULT_SETTINGS`, validate in `normalizeSettings`, allow the key in
`dashboard-service.updateSettings`, apply any engine-side effect (DNR, alarms,
pruning) and test both the store and the effect.

## Known limitations (do not "fix" by accident)

- YouTube video ads cannot be blocked without broad cosmetic access WebGuard
  deliberately does not take.
- Blocking is host/path level; some ad slots need cosmetic filtering.
- Blocklists only catch known threats; matching is offline. "Not found" is never
  "safe".
- TLS certificate details are unavailable to extensions.
- The GitHub scheduled workflow auto-disables after 60 days of repository
  inactivity; `keepalive.yml` prevents that.
- Per-tab live dedupe is in memory: a service-worker restart during a page visit can
  recount a retry storm for the popup (stored counts stay deduped).
